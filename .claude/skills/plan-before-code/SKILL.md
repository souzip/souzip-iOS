# Plan Before Code 워크플로우

## 핵심 원칙

**플랜이 명시적으로 승인되기 전까지 절대 코드를 작성하지 않는다.**

목적:
1. 아키텍처와 중요한 결정의 주도권을 개발자가 쥐기
2. 잘못된 방향으로 구현된 코드를 나중에 뜯어고치는 낭비 방지

---

## 단계별 프로세스

### 1단계: 리서치 + 플랜 작성 (한 번에)

코드를 **깊이 파악**하고 구현 계획까지 한 번에 작성한다.
표면적인 함수 시그니처 훑기가 아닌 끝까지 추적한다.

**해야 할 것:**
- 변경이 영향을 줄 코드 경로를 끝까지 추적
- 기존 패턴, 추상화, 의존성 파악
- 변경 시 함께 수정해야 할 연관 파일
- 주목할 위험 요소 (사이드 이펙트, 강한 결합 등)

**하지 말아야 할 것:**
- 플랜 작성 후 바로 구현 시작 — 반드시 사용자 승인 대기

---

### 2단계: 피드백 반영 (`"메모 반영해서 업데이트해"`)

사용자가 plan.md 내 특정 위치에 인라인 메모를 추가하면, 그 메모를 반영해 플랜 문서만 업데이트한다.

**이 단계에서 코드 작성은 금지다.**

인라인 메모 패턴 예시:
- 잘못된 가정 교정: "이건 PUT이 아니라 PATCH야"
- 접근 방식 거부: "이 부분 제거해. 캐싱 필요 없어"
- 도메인 규칙 주입: "Visibility는 개별 아이템이 아니라 리스트에 있어야 해"
- 범위 축소: "다운로드 기능은 지금 안 해. 플랜에서 빼줘"

사용자가 만족할 때까지 1–2단계를 반복한다.

### 3단계: 구현 (`"구현해"` / `"구현 시작해"`)

이 명시적 지시 이후에만 코드를 작성한다.

**구현 방식:**
- 승인된 플랜만을 기준으로 기계적으로 구현
- 완료된 항목은 플랜 문서에서 체크 표시
- 구현 도중 새로운 판단이 필요하면 구현 멈추고 사용자에게 확인

**방향이 틀어졌을 때:**
패치를 쌓지 말고 git으로 되돌린 뒤 플랜을 재설정한다.

## 트리거 단어 요약

| 사용자 지시 | Claude 행동 |
|-------------|-------------|
| 작업 요청 (리서치/플랜/구현 전부) | 리서치+플랜을 한 번에 작성, 대기 |
| `"메모 반영해서 업데이트해"` | 플랜 문서만 수정, 코드 작성 금지 |
| `"구현해"` / `"구현 시작해"` | 승인된 플랜 기준으로 코드 작성 시작 |

---

## 산출물 위치

```
docs/plans/
└── {feature}/
    └── plan.md       # 리서치 결과 + 구현 계획
```

- `{feature}`는 구체적으로 작성해 중복을 방지한다
  - `geocoding-to-location-address` (✅ 구체적)
  - `refactor` (❌ 너무 범용적)
- `docs/plans/` 디렉토리가 없으면 생성한다
- 같은 이름의 폴더가 이미 존재하면 덮어쓴다

---

## plan.md 포맷

```markdown
# {feature} 리서치 및 구현 계획

## 파악한 구조
- 호출 체인, 의존성, 기존 패턴 등 간결한 배경 설명

## 변경 계획

### 파일경로/파일명.swift
**변경 이유:** 왜 이 파일을 변경하는지 한 줄 설명

**Before:**
\```swift
// 실제 현재 코드 (변경 범위 중심으로 발췌)
\```

**After:**
\```swift
// 변경 후 코드
\```

### 다른파일.swift
(동일 포맷 반복)
```

**작성 기준:**
- Before/After에 실제 코드를 발췌해 검토자가 눈으로 변경을 확인할 수 있게 한다
- 전체 파일이 아니라 변경 범위 중심으로 발췌한다
- 각 파일이 "왜 변경하는지"를 한 줄로 설명한다
- 추상적인 방향성 나열이 아닌, 구체적인 코드 변경을 보여준다

## 단순 작업 예외

다음은 이 워크플로우 없이 바로 진행 가능:
- 오타/오류 수정
- 한 줄 버그 픽스
- 명확하게 범위가 정해진 단순 변경

판단이 애매한 경우 사용자에게 "이 작업 리서치/플랜 단계 먼저 할까요?"라고 확인한다.
