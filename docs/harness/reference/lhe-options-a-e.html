먼저 읽기 — LHE와 Souzip이 만나는 지점

두 하네스는 대체가 아니라 합성입니다.

LHE 최소 팩 상태·기능·기준선·DoD·증거
Souzip (지금) 5모드·G1~G5·plan Before/After
합치면 승인 주도권 + 세션 연속성
[LHE 닫힌 루프] 읽기(progress + feature) → 기준선(init) → 구현 → 검증+증거 → 기록 → 다음 세션 [Souzip 닫힌 루프] plan(G1) → 승인 → implement → verify(G3) → ship(G4)

A~E는 “LHE에서 뭘 가져올지” 고르는 메뉴입니다. 여러 개 골라도 되고, 한 번에 하나만 넣는 것을 권장합니다.

A progress — 세션 이어 받기

LHE: claude-progress.md → Souzip 후보: harness/progress.md

무엇인가?

시간·세션 축의 단일 진실 원천(SSOT)입니다. “지금 저장소가 검증된 상태인가”, “다음 세션은 뭘부터 할까”, “지난 세션에서 뭘 했는가”를 채팅이 아니라 파일에 남깁니다.

LHE 파일 구조 (두 블록)

블록내용갱신 시점
Current Verified State 루트 경로, 시작 명령, 검증 명령, 최우선 미완 기능, 현재 blocker 검증 상태가 바뀔 때마다 항상 1벌만 최신으로
Session Record Goal, Completed, Verification run, Evidence, Commits, Known risks, Next action 세션 종료마다 항목 하나 추가
[새 Cursor 채팅 시작] │ ▼ harness/progress.md 읽기 ──► "Next: wishlist M4 plan 메모 반영" │ ▼ (채팅 없이도) 어디서 이어갈지 알 수 있음

Souzip 지금 vs A 적용 후

지금A 적용 후
임시 메모 harness/state/ (gitignore, 버려짐) harness/progress.md (커밋, 이어 받기용)
기능 범위 plan.md에만 progress = 세션·전역, plan = 그 기능 구현
5모드 그대로 세션 시작 = intake/plan 전에 progress 읽기 추가
Souzip에 넣을 때 최소 diff
파일 1개 + AGENTS.md / 00-triggers.md에 “새 세션 → progress 먼저” 한 줄. state/는 당일 스크래치만 유지 가능.

장점

  • 새 채팅마다 저장소 재탐색 감소
  • vision §성공 2 (문서화)와 직결
  • LHE 5레이어 중 상태 관리 채움

부담

  • 세션 끝에 2~3분 기록 필요
  • 안 쓰면 stale — “읽되 안 쓰면” 무용

B feature_list + evidence — 기능·완료 증거

LHE: feature_list.json → Souzip 후보: docs/plans/{feature}/feature-tracker.json

무엇인가?

기능 축의 SSOT입니다. PRD·milestones를 “에이전트가 기계적으로 읽고 갱신”할 수 있는 카드 목록으로 둡니다. 핵심은 status와 evidence — 코드를 썼다고 passing이 되지 않습니다.

기능 카드 한 장의 필드

필드의미
id, priority, area식별·우선순위·영역 (예: wishlist, mypage)
user_visible_behavior사용자 눈에 보이는 “완료” 모습
statusnot_started · in_progress · blocked · passing
verification확인 절차 (단계별, 예: 빌드, 화면 수동 확인)
evidence실제로 verification을 돌렸다는 기록

규칙: in_progress는 동시에 하나만. 반쯤 된 기능이 여러 개면 에이전트가 산만해집니다.

plan.md (Before/After) feature-tracker.json "어떻게 고칠지" "이 기능 전체가 끝났는지 + 증거" │ │ └────────── verify ──────────┘ evidence 기록 후 passing

Souzip 지금 vs B 적용 후

지금B 적용 후
범위·완료 milestones.md + plan 체크박스 (사람 위주) JSON + evidence (에이전트·검증 위주)
모든 작업에 — 큰 기능만 (wishlist M4 등). Quick Flow·한 줄 버그는 생략
G3 verify 체크리스트 5개 “evidence 없으면 passing 금지” 연동

장점

  • “완료했어” vs 실제 완료 검증 격차 축소
  • 여러 마일스톤을 한 기능 단위로 추적

부담

  • JSON 유지 비용 · 작은 수정에는 과함
  • docs/plans/가 gitignore면 팀 공유는 별도 정책 필요

C AGENTS 루틴 + Definition of Done

LHE: AGENTS.md 섹션 → Souzip: AGENTS.md + plan.md 보강

무엇인가?

“코드 쓰기 전·후에 무조건 하는 일”과 “끝났다의 정의”를 진입점 파일에 고정합니다. 5모드(G1~G5)와 겹치지 않고 보완합니다.

LHE AGENTS.md 네 덩어리

  1. Startup Workflow — progress 읽기 → feature 선택 → init → 기준선 검증
  2. Working Rules — 한 번에 한 기능, 증거 없이 완료 표시 금지
  3. Definition of Done — 4조건 (구현 · 검증 실행 · 증거 기록 · 재시작 가능)
  4. End of Session — progress/feature 갱신 · blocker 기록 · clean 상태

Souzip에 넣는 실제 모습

LHE 섹션Souzip 대응
Startup AGENTS.md + (A 있으면) progress 읽기
Working Rules 이미 00-triggers.md · G1·G2 — 중복 최소화
DoD 각 plan.md에 ## 완료 기준 (기계 검증 가능 bullet)
End of Session verify/ship 전 checklist 5줄 (A·B와 연동)
## 완료 기준 (plan.md 예시) - [ ] MyPageLikedTab 2열 그리드, mock 6개 표시 - [ ] Xcode scheme Souzip Debug 빌드 성공 (증거: 빌드 로그 한 줄) - [ ] Presentation → Data import 없음 (verify)

장점

  • 가장 가벼움 — 문서 섹션만 추가
  • 고통 1 (plan 검토) + G3와 직결

부담

  • DoD를 대충 쓰면 형식만 늘어남 — 구체적이어야 함

D init / preflight — 환경·기준선

LHE: init.sh → Souzip 후보: harness/scripts/preflight.sh

무엇인가?

새 기능을 쌓기 전에, 저장소가 “이미 망가져 있지 않은지” 확인하는 스크립트입니다. LHE 실패 레이어 ③ 실행 환경을 코드로 고정합니다.

LHE init.sh가 하는 일

  1. 현재 디렉터리 출력 (위치 확인)
  2. 의존성 설치 (INSTALL_CMD)
  3. 검증 실행 (VERIFY_CMD) — 실패 시 중단
  4. (선택) 개발 서버 시작 명령 출력

Souzip iOS에 맞게 바꾸면

LHE 변수Souzip 예시 (합의 필요)
INSTALL_CMDtuist install
VERIFY_CMD (가벼운)tuist generate 성공
VERIFY_CMD (무거운)Xcode build (scheme·시간 합의 후)
START_CMDXcode에서 Souzip.xcworkspace 열기 안내
implement 요청 │ ▼ ./harness/scripts/preflight.sh │ ├─ 실패 → "기준선부터 고칠까요?" (새 기능 X) └─ 성공 → plan 구현 시작

장점

  • 에이전트가 tuist/경로에서 헤매는 시간 감소
  • “완료”인데 빌드 안 되는 상황 조기 발견

부담

  • Xcode CLI 환경·scheme 설정 필요
  • 로컬마다 다르면 스크립트 조정 필요

E 전부 — 단, 한 번에 하나씩 순서만 정함

LHE 최소 팩 4종 + 선택 파일을 Souzip 5모드 위에 합성

합성 후 큰 그림

┌─────────────────────────────────────────────────────────┐ │ AGENTS.md (C: Startup / DoD / End) │ └───────────────────────────┬─────────────────────────────┘ │ ┌──────────────────────┼──────────────────────┐ ▼ ▼ ▼ progress.md (A) feature-tracker (B) preflight.sh (D) │ │ │ └──────────────────────┼──────────────────────┘ ▼ harness/workflows/00-triggers.md intake → plan → implement → verify → ship │ ▼ docs/plans/{feature}/plan.md + ## 완료 기준 (C)

E를 선택했을 때 권장 순서 (천천히)

  1. C — plan에 ## 완료 기준 (가장 가벼움)
  2. A — harness/progress.md
  3. D — preflight (tuist generate부터)
  4. B — 큰 기능 1개로 feature-tracker 시범
  5. 선택: session-handoff, clean-state, evaluator-rubric

E ≠ 한 번에 전부 구현. “구조는 LHE처럼 가고 싶다”는 방향 선택이고, 실제 반영은 위 순서대로 마일스톤 하나씩이 안전합니다.

한눈에 비교 · 다음 액션

옵션 LHE 원본 막는 고통/레이어 난이도 Souzip 우선순위 (E일 때)
A progress claude-progress.md 세션 끊김 · 상태⑤ 중 2번째
B feature+evidence feature_list.json 조기 완료 · 검증④ 중~상 4번째
C DoD·루틴 AGENTS.md 섹션 완료 모호 · 명세① 하 1번째
D preflight init.sh 환경③ 중 (Xcode) 3번째
E 전부 최소 팩 전 레이어 순차 C→A→D→B

당신이 할 일 (판단용)

  1. 브라우저로 이 HTML 열기
  2. A~E 중 먼저 넣고 싶은 것에 mental check
  3. 이 설계 세션에 예: “C부터, E 방향” 한 줄 전달
  4. 그때 그 한 옵션만 harness에 반영 요청
