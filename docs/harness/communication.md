# 말하는 방식 (어투)

> 사용자·에이전트가 **이해하기 쉽게** 말하고 쓰기 위한 규칙.
> 진입: [`AGENTS.md`](../../AGENTS.md) · Git 추적 ✅

---

## 왜 있나

설명이 짧아도, **낯선 단어가 많으면** 한 번에 안 들어온다.
이 문서는 “보고서 말투” 대신 **평소에 작업 설명하듯** 맞추기 위함이다.

---

## 사용자에게 답할 때

1. **왜** 그런지 먼저, 폴더·파일 이름은 그다음
2. **평소 말투** — 기획서·논문처럼 쓰지 않는다
3. 길이보다 **이해**가 우선 (필요하면 문단으로 풀어 쓴다)
4. 영어나 전문 용어는 **처음에 한 번 풀어 쓴다**
   - legacy → 예전 방식
   - worktree → 코드만 따로 두는 작업 폴더
5. **표·체크리스트**는 비교·선택이 필요할 때만
6. **존댓말** (한국어)

### 피하는 표현 (맥락 없이 단독 사용)

정본, 격리, 고도화, 산출물, SSOT, 레버, 게이트, 페이즈, 워크플로우 정합, …

→ 꼭 써야 하면: **쉬운 말 + 괄호**
예: “지금 따라야 할 문서(`workflow/story-plan-session.md`)”

### 나쁜 예 → 좋은 예

**나쁜**

> Phase 2에서 workflow 정본을 legacy와 격리하여 SSOT를 확정함.

**좋은**

> 지금 쓰는 작업 순서 설명은 `workflow/`에 모았어요. 그래서 작업 흐름을 확인할 때는 그 폴더부터 보면 됩니다.

---

## 하네스 문서·스킬을 쓸 때

사용자 답변과 **완전히 똑같을 필요는 없다**. 문서는 조금 더 정리돼도 된다.

다만 같은 원칙을 따른다.

- 제목·한 줄 요약으로 **이 파일이 뭔지** 먼저
- 내부 용어(Story, plan, Goal)는 **처음 나올 때 한 줄 설명**
- ROADMAP·ADR는 “완료/대기” 정도는 표 OK, **설명 본문은 문단**
- 새 단어를 만들기보다 **이미 쓰는 말** 유지 (Story, plan, goal)

---

## 이 문서를 바꿀 때

예시 문장을 **실제로 쓰기 좋았던 대화**로 바꿔 두면, 이후 에이전트가 더 잘 맞춘다.
