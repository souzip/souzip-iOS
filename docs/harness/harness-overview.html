Codex 기준 Souzip Harness

작업 전 합의, 작은 PR, 검증까지 포함하는 기능 개발 흐름

이 하네스는 Souzip 기능 작업을 바로 구현하지 않고, Goal 인터뷰로 의도를 분명히 한 뒤 Story와 Plan으로 나누고, 각 Plan을 검증 가능한 단위로 끝내기 위한 기준입니다.

  • Goal 승인 전에는 Story, Jira, worktree, Plan으로 넘어가지 않습니다.
  • Story 하나는 worktree 하나이자 PR 하나입니다.
  • Plan은 한 세션에서 구현과 검증까지 끝낼 수 있어야 합니다.
  • commit은 “커밋해”, PR 생성과 PR용 push는 “PR” 지시 뒤에만 합니다.

전체 흐름

1. Goal 인터뷰질문은 한 번에 1~3개만 하고, 목표와 이해관계를 명확히 합니다.
2. Goal 승인사용자가 자연어로 명확히 동의하면 승인으로 봅니다.
3. Story 후보전체 후보를 만들되 Jira는 active 1~2개만 생성합니다.
4. WorktreeStory worktree는 항상 develop에서 만듭니다.
5. Plan세션 안에서 구현과 검증까지 가능한 크기로 나눕니다.
6. 구현사용자가 “구현해”라고 한 뒤 Plan 범위 안에서만 고칩니다.
7. 검증verify.sh로 포맷, lint, generate, build, 관련 테스트를 확인합니다.
8. PRdevelop 변경 파일 겹침을 확인한 뒤 사용자가 “PR”이라고 하면 진행합니다.

작업 단위

Goal

기능 목표와 이해관계

무엇을 왜 바꾸는지, 성공 기준과 하지 않을 범위를 정합니다.

  • 한 줄 목표
  • 사용자와 이해관계
  • 성공 기준
  • Story 후보
Story

PR 하나의 단위

기본은 기술 경계로 나누고, 너무 크면 사용자 가치 기준으로 다시 나눕니다.

  • worktree 하나
  • Jira Story 하나
  • PR 하나
  • target branch: develop
Plan

한 세션의 실행 단위

사용자 승인 뒤 구현하고, 검증 결과가 있어야 닫을 수 있습니다.

  • 구현 범위
  • 하지 않을 것
  • 검증 명령
  • 실행 결과

Story 선택 기준

첫 번째 active Story

작지만 끝단 흐름을 실제로 연결해 볼 수 있는 Story를 고릅니다.

  • API, 도메인, 저장, UI 중 필요한 경로가 이어짐
  • 작은 PR로 앱이 깨지지 않음
  • 다음 Story의 기준을 만들어 줌

두 번째 active Story

필요하면 가장 불확실한 기술 리스크를 검증하는 Story를 고릅니다.

  • 나중에 막히면 설계가 흔들릴 수 있음
  • 기술 가능성을 먼저 확인해야 함
  • 너무 크면 Jira와 worktree 전에 다시 쪼갬

검증

Plan은 구현만 끝났다고 닫지 않습니다. 방금 실행한 검증 명령과 결과가 있어야 합니다.

docs/harness/scripts/verify.sh plan

VERIFY_TEST_TARGETS="DomainTests" docs/harness/scripts/verify.sh plan
VERIFY_TEST_SCHEME="Domain" docs/harness/scripts/verify.sh plan
  • SwiftFormat lint
  • SwiftLint
  • Tuist generate
  • Tuist build
  • 관련 테스트
  • Plan 밖 요구가 생기면 Plan을 먼저 고칩니다.
  • Tuist, Factory, 모듈 경계, 레이어 규칙 변경은 멈추고 묻습니다.
  • 같은 실패를 두 번 이상 고쳐도 해결되지 않으면 원인 조사로 전환합니다.

PR 전 develop 변경 확인

Story 작업 중 develop이 바뀔 수 있으므로 PR 전에 변경 파일이 겹치는지 확인합니다. 겹치는 파일이 있으면 멈추고 사용자에게 알립니다. 

git fetch origin develop
git diff --name-only {base_commit}..origin/develop
git diff --name-only {base_commit}..HEAD
두 변경 파일 목록이 겹치지 않으면 Story 종료 검증 결과를 유지하고 PR로 갈 수 있습니다. 겹치면 Plan이나 구현이 낡았을 수 있으므로 사용자 판단이 필요합니다.

워크플로우 스킬

스킬 쓰는 시점 막는 선
souzip-goal 기능 아이디어를 Goal로 만들 때 Story, Jira, worktree, Plan, 코드로 넘어가지 않음
souzip-story 승인된 Goal을 Story 후보와 active Story로 나눌 때 모든 Jira Story를 한 번에 만들지 않음
souzip-plan 선택된 Story를 한 세션 Plan으로 나눌 때 “구현해” 전 코드 수정하지 않음
souzip-verify Plan 또는 Story 검증과 실패 분류가 필요할 때 방금 실행한 검증 없이 완료라고 말하지 않음
souzip-commit 사용자가 “커밋해”라고 했을 때 <type>: <한국어 설명> 한 줄 형식 유지
souzip-pr 사용자가 “PR”이라고 했을 때 develop 변경 파일 확인 뒤 PR용 push와 PR 생성
구현 스킬은 아직 만들지 않습니다. 구현은 승인된 Plan과 사용자의 “구현해” 지시 아래에서만 진행합니다.

서브에이전트

역할 쓰는 시점 유형
researcher 레퍼런스나 로컬 문서를 조사할 때 독립형, 필요 시 병렬형
interviewer Goal 질문과 초안을 만들 때 독립형
story-splitter Goal을 PR 단위 Story로 나눌 때 독립형
planner Story를 세션 단위 Plan으로 나눌 때 독립형
implementer 승인된 Plan을 구현할 때 독립형
verifier 검증과 실패 분류를 맡길 때 독립형, 필요 시 병렬형
