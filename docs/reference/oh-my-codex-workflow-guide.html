oh-my-codex(OMX) 워크플로우

OpenAI Codex CLI 위에 얹는 멀티에이전트·플랜·상태 오케스트레이션 레이어.
Codex를 대체하지 않고, 클라리파이 → 플랜 합의 → 실행 → 리뷰 → QA 순서를 강제·자동화한다.

Codex 전용 $ 키워드 .omx/ 지속 상태

세션 안에서 $deep-interview → $ralplan → $ultragoal 이 권장 기본 경로이다. 큰 작업·고위험 작업은 중간에 $prometheus-strict, 마무리는 $code-review + $ultraqa.

1. OMX란 무엇인가

oh-my-codex(OMX)는 npm 패키지 oh-my-codex로 설치하며, 실행 엔진은 항상 Codex CLI다. Cursor·Claude Code·VS Code 확장이 아니다.

정신 모델 OMX는 Codex를 바꾸지 않는다. OMX는 더 나은 라우팅 + 재사용 워크플로 + 런타임(팀·HUD·상태)을 붙인다. 하루 종일 omx 명령을 치는 도구라기보다, Codex 세션 안에서 $스킬을 부르는 방식으로 쓴다.
구성 요소역할
Codex CLI실제 코딩·도구 호출·모델 대화
AGENTS.md프로젝트 지침(OMX가 기본으로 레이어)
~/.codex/prompts/33+ 역할 프롬프트 (architect, executor, critic 등)
~/.codex/skills/*/SKILL.md37 workflow 스킬 ($ralplan 등)
.omx/플랜, 로그, 메모리, ultragoal ledger, 팀 worktree 메타
MCP 서버 (5종)상태·메모리·코드 인텔·트레이스 등 세션 간 지속

2. 구조 한눈에

사용자 │ ▼ omx (런처) ──► Codex CLI 세션 │ ├── AGENTS.md ← 프로젝트 두뇌(지침) ├── ~/.codex/prompts/ ← 역할 카탈로그 (/prompts:name) ├── ~/.codex/skills/ ← 워크플로 ($ralplan 등) ├── ~/.codex/config.toml └── .omx/ ← 런타임 상태·플랜·로그·ultragoal

omx setup이 프롬프트·스킬·hooks·config를 설치한다. omx doctor는 설치 형태만 검증한다 — 실제 API 호출 성공은 codex login status + omx exec ... OMX-EXEC-OK로 따로 확인해야 한다.

3. 설치·세션 시작

npm install -g @openai/codex    # Codex가 없을 때만
npm install -g oh-my-codex
omx setup
omx doctor
codex login status
omx exec --skip-git-repo-check -C . "Reply with exactly OMX-EXEC-OK"

권장 런치 (git 프로젝트)

omx --worktree=feat/my-task --madmax --high
플래그의미
--worktree=name별도 git worktree에서 Codex 실행 (현재 checkout 오염 방지)
--madmaxCodex 샌드박스·승인 우회 — 신뢰 repo만
--high추론 effort high
--directtmux/HUD 없이 일반 터미널에서 Codex만
동시에 여러 --madmax 세션 같은 디렉터리에서 돌리지 말 것. 세션마다 --worktree=다른-이름을 쓴다.

세션이 열리면 Codex 채팅 안에서 $... 스킬을 입력한다 (터미널이 아님).

4. 정석 워크플로우 (Canonical Workflow)

공식 Skills 문서의 권장 완주 경로:

$deep-interview → $ralplan → $prometheus-strict (고위험만) → $ultragoal → $code-review → $ultraqa
[모호함] [플랜 잠금] [실행·검증] [머지 준비] │ │ │ │ $deep-interview ──► $ralplan ──► ($prometheus-strict) ──► $ultragoal ──► $code-review ──► $ultraqa │ │ │ │ │ │ │ └── 필요 시 $team (병렬) │ └── Architect 증거 → Critic 증거 필수 └── 경계·비목표·의도
가장 중요한 게이트 $ralplan은 플랜 산출물 + 합의 증거에서 끝난다. PRD/테스트 스펙 파일만 있다고 통과가 아니다. Architect 리뷰 증거 → Critic 리뷰 증거가 기록되어야 실행으로 넘길 수 있다. 코드 변경은 $ultragoal, $team, 또는 의도적인 $ralph에서만.

5. 단계별 상세

PHASE 1

$deep-interview — 요구 명확화

언제: 요청이 흐리거나, 범위·비목표·이해관계가 불명확할 때.

하는 일: 소크라테스식 질문으로 의도, 경계, 하지 않을 것을 고정한다.

산출: 인터뷰 메모·요구 정리 (이후 $ralplan의 입력).

$deep-interview "clarify the authentication change"

코드 변경: 없음 (클라리파이만).

PHASE 2

$ralplan — 플랜 합의·트레이드오프

언제: 인터뷰 후, 구현 전에 아키텍처·구현 순서·리스크를 문서화할 때.

내부 역할: planner / architect / critic 등이 관여. 개념이 무거우면 scholastic(온톨로지·가정 검토) 자문 증거를 따로 남길 수 있음.

완료 조건:

  • 승인 가능한 구현 플랜·트레이드오프 문서
  • Architect 리뷰 증거 기록
  • 이어서 Critic 리뷰 증거 기록
$ralplan "approve the auth plan and review tradeoffs"

코드 변경: ❌ — ralplan은 직접 구현하지 않는다.

PHASE 2b (선택)

$prometheus-strict — 고위험 플랜 강화

언제: 보안·마이그레이션·대규모 리팩터 등 실패 비용이 클 때.

하는 일: Metis(명확화) → Momus(비판) → Oracle(종합) 스타일의 인터뷰·비판·합성으로 플랜을 압축 검증.

산출: .omx/plans/prometheus-strict/ 아래 durable plan (필요 시).

이후 $ultragoal 또는 $team으로 handoff.

PHASE 3

$ultragoal — 지속 목표·ledger 실행 기본 실행 경로

언제: ralplan(± prometheus)으로 승인된 플랜을 실제로 밀어붙일 때.

하는 일:

  • 승인 플랜을 Codex goal + .omx/ultragoal ledger 체크포인트로 쪼갬
  • 스토리 단위로 진행·검증·상태 갱신
  • 병렬이 이득인 스토리만 그 안에서 $team 호출
$ultragoal "turn the approved plan into durable Codex goals"

vs $ralph: ultragoal은 다중 goal·ledger가 기본. ralph는 단일 소유자 루프 레거시/의도적 대안.

PHASE 4

$code-review — 머지 전 리뷰

스타일·품질·API·보안·성능 등 축을 가진 리뷰어 에이전트를 활용. 브랜치·diff 기준으로 “머지 가능한가” 판단.

$code-review "review current branch"
PHASE 5

$ultraqa — 테스트·검증·수정 루프

적대적 QA 관점에서 테스트 실행, 실패 수정, 증거 수집까지 반복. visual 작업은 $visual-verdict 등 보조 스킬과 연계.

6. 실행 모드 비교

플랜 승인 이후 어떤 “엔진”으로 밀지 고르는 표:

스킬 한 줄 적합한 경우 주의
$ultragoal 다중 goal + ledger 체크포인트 기본 권장 — 긴 기능, 여러 납품 단위 .omx/ultragoal 아티팩트 유지
$ralph 끝날 때까지 자기참조 루프 + verifier 단일 작업을 한 소유자가 끝까지 ledger 없이 “끝까지” 밀 수 있음 — 방향 이탈 위험
$team N:role N명 worker 병렬 + worktree 격리 독립 파일/모듈 병렬 구현 tmux·merge·integration-report — 운영 복잡
$autopilot 전 구간 자동: interview→ralplan→ultragoal→review→qa 신뢰 repo + 명확한 완료 정의 리뷰/QA 불량 시 planning으로 회귀. ralplan 합의 전 이탈 금지
$ultrawork 최대 병렬 시간 압박·독립 태스크 많음 토큰·충돌 비용 큼

README 권장 한 줄 요약

  1. 모호하면 $deep-interview
  2. 플랜·트레이드오프 승인은 $ralplan
  3. 실행은 기본 $ultragoal — 스토리 안에서만 $team
  4. 의도적으로 단일 루프면 $ralph

7. $team · worktree 병렬

v0.13+부터 팀 worker는 기본적으로 전용 git worktree에서 돈다. 플래그 없이도 .omx/team/<name>/worktrees/worker-N 격리.

Leader (원본 또는 launch worktree, 깨끗하게 유지) │ ├── worker-1 @ worktree-1 (detached branch, 자동 commit) ├── worker-2 @ worktree-2 └── worker-3 @ worktree-3 │ ▼ Leader: merge / cherry-pick / rebase 전략으로 통합 → integration-report.md (충돌 조기 보고)
# Codex 세션 안
$team 3:executor "refactor auth module"

# CLI (운영자)
omx team 3:executor "fix the failing tests"
omx team status <team-name>
omx team resume <team-name>
omx team shutdown <team-name>

혼합 CLI: OMX_TEAM_WORKER_CLI_MAP=codex,claude,gemini 로 worker마다 다른 CLI 가능 (고급). macOS/Linux에서는 tmux + HUD가 권장 런타임이다.

8. .omx/ — 무엇이 남는가

OMX의 “세션 간 기억”은 주로 디렉터리 + MCP로 구현된다.

경로/개념용도
.omx/plans/ralplan, prometheus-strict 등 플랜 아티팩트
.omx/ultragoal/goal ledger, 체크포인트, handoff
.omx/team/팀 run 메타, worktree, integration 리포트
.omx/hooks/플러그인 훅 (Codex lifecycle)
로그·메모리·트레이스MCP state/memory/trace 서버와 연동
omx_wiki/프로젝트 위키(마크다운·검색 우선, 벡터 아님)

런치 worktree(OMX 바깥): ../.omx-worktrees/<name> — omx --worktree=feat/foo 시 named branch/worktree 생성.

9. 에이전트(역할) 카탈로그 요약

Codex 안에서 /prompts:architect 같은 형태로 specialist를 부른다. 정석 플로우 이후 “특정 레인이 필요할 때” 사용.

11. 리서치 vs 플랜 경계

스킬역할다음 단계
$best-practice-research 공식 문서·릴리스 노트·표준 인용 근거 결과를 $ralplan 입력으로만 넘김
$autoresearch 검증기 통과해야 끝나는 리서치 산출물 통과 artifact → ralplan
$autoresearch-goal goal 모드 + professor/critic 검증 리서치 장기 리서치 미션
$ralplan 아키텍처·구현 플랜 합성 증거 충족 후 ultragoal/team

12. $autopilot 전체 루프

사람이 단계마다 $를 치지 않고, OMX가 단계를 강제하는 “최대 자동” 모드:

$deep-interview ↓ $ralplan ← Architect 증거 + Critic 증거 없으면 진행 불가 ↓ $ultragoal (+ 필요 시 $team) ↓ $code-review ── 불량 ──► planning 으로 회귀 ↓ $ultraqa ── 불량 ──► planning 으로 회귀 ↓ 완료
사이드 프로젝트·방향 통제가 중요하면 autopilot/ralph를 기본으로 쓰기보다 단계별 $ 호출 + 사람 승인이 안전하다.

13. Cursor 이식(B)할 때 기억할 점

이 문서는 OMX 원본 설명이다. Cursor만 쓸 때는 아래가 그대로 안 옮겨진다:

  • omx / tmux HUD / omx team worktree 자동화
  • OMX MCP 5종 (파일 + 규칙으로 근사 가능)
  • $ralph·$autopilot 무인 완주 루프
  • Codex 전용 /prompts:role 33종 전체

옮기기 좋은 핵심: 단계 순서, ralplan 전 코드 금지, Architect/Critic 승인 개념, 플랜·goal·리뷰·QA 문서를 디스크에 남기기.
